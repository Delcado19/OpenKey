# AJAZZ AK35i V4 ISO-DE — owner research and implementation handoff

Date: 2026-11-25. Target: Delcado19/OpenKey, based on upstream OpenKey 0.2.0. This is research, not a supported-device declaration. Keep the upstream architecture and submit a narrowly scoped contribution once verified.

## Evidence and source material

The owner has a proprietary (non-QMK) AK35i V4, 105-key German ISO, with TFT and encoder. Vendor desktop installer is misleadingly named AK45I V4. Native wired typing and 2.4 GHz typing work after official firmware update 1.02 to 1.09 and re-pairing. Do not flash, reset, or change receiver firmware for this project.

Primary companion data: [owner RGB captures and LED map](../../fixtures/diagnostics/ak35i-v4-owner-rgb-captures.json). This is copied from the owner's Lighting Studio research, not generated by OpenKey or by the new driver. It uses full 64-byte feature payloads, no report-ID prefix, selected vendor-driver transactions, and 105 LED geometry entries. The second Direct RGB transaction intentionally ends before the last GET; do not invent it. Full native protocol notes: [Lighting Studio specification](https://github.com/Delcado19/msi-mystic-light/blob/master/docs/AJAZZ_AK35I_V4_PROTOCOL.md). Cross-check any inferred value with source capture and repeat after firmware update. Captures are not proof of new OpenKey writes. Original raw captures and vendor binaries are not committed to this public fork.

Evidence levels: VERIFIED = owner directly observed V4 behavior; CAPTURED = vendor-driver trace from owner hardware; REFERENCE = another board / upstream static analysis; INFERRED = plausible but untested; PROPOSED = implementation decision. Upstream VERIFIED for AK820 hardware does not carry over to V4. Record test results per function and firmware. Avoid reclassifying experimental functions merely because protocol selection succeeds.

## 1. Owner USB diagnostics — verified

OpenKey 0.2.0, Windows 11, Chromium 158, secureContext=true, webHID=true. VID:PID 0C45:8009, product USB KEYBOARD, manufacturer unknown, firmware unknown in WebHID (bcdDevice not exposed). | Collection | Input report ID:size | Output | Feature |
|---|---|---|---|

| FFFF:0001 | 5:3 | none | none |

WebHID sizes exclude report-ID byte. Native hidapi may prepend ID 0; existing transport handles this. Do not prepend a zero in the codec. No GET_FEATURE on FF68; it has no feature report. V3 reference warns of a firmware crash if queried incorrectly.

Owner's complete observed OpenKey session had only these three operations (each 64 bytes, report ID 0, FF13:0001):
| t(ms) | Operation | Payload prefix, zero padded | Duration |
|---:|---|---|---:|
| 9 | GET | 00 00 00 00 | 2.3ms |
| 47 | SET | 04 18 00 00 | 2.0ms |
| 87 | GET | 04 18 00 01 | 2.0ms |

Successful official START acknowledgement; no other OpenKey functionality tested on this unit. No data-pipe transfer yet. QMK/VIA candidate skipped (no FF60:0061); online AA55 candidate skipped because FF68 output is 4096 rather than <=64; CRS candidate skipped (not VID 1A2C FF02); receiver candidate skipped. The browser key tester is unrelated to VIA compatibility.

Receiver support bundle 0C45:FEFE: only 000C:0001 input ID8:2 and ID17:1, 0001:000E input ID9:8 visible, no output/features, adapter null, confidence LOW, candidates empty, trace []. Catalogue AK820 Pro/MAX Bluetooth name is not a match. Configuration over receiver and Bluetooth remains unknown, not supported in V4 profile. Never send wired commands to receiver. ## 4. ISO-DE layout

Use all 105 entries from companion led_map, preserve array order exactly. Rect values are manufacturer image coordinates, not key units; normalize geometry using observed pitch (~33–34px) and consistent origin, adjust ISO Enter outline visually without altering wire ID. Use existing KeyboardLayout types, labels appropriate to German ISO (Y/Z, umlauts, sharp S, ISO extra key). HID usage represents physical usage not localized character. Do not derive LED IDs from usage or label.

Examples: Esc light1 usage29 hex; F1 light2; ISO extra key light111 usage64 hex; ISO Enter light85 usage28 hex; Backspace103, space94; full nav and numpad. LED map includes a vendor usage AF for one key; do not assume it is standard keyboard-page Fn or a valid remap target. The fixture records light_index, not authoritative keymap slot; verify original XML key_index before allowing remapping. Until then slot must be treated as unverified (use null if schema allows, or display-only tentative mapping with all keymap writes blocked). Knob/TFT are not extra RGB keys. Test exactly 105 unique light IDs, sparse maximum123, ordered mapping, non-overlapping intended geometry and German legends.

## 5. RGB protocol comparison with existing code

All offsets zero-based payload, 64-byte Feature SET/GET on FF13 ID0. Header 04/opcode, ACK echoes opcode and status byte3=01. Fixture operation order is authoritative for captured transactions; additional ACK bytes may be nonzero. See companion JSON and linked detailed specification.

### Direct RGB
Existing encodeRealtimeTable packs [led,r,g,b] into 512 bytes; preserve **XML order**, 105 records then 23 zero records, eight 64-byte chunks including last all-zero chunk. Do not rely on Object.entries numeric sorting. Current streamRealtime uses Cmd.REALTIME_RGB arg8=8, sendTable, Cmd.SAVE and requireAck:false for both commands. V4 capture shows SET 04 20 arg8=8, GET acknowledged, eight SET chunks, SET 04 02, GET acknowledged; no F0. For V4 use strict ACK checking and exact length/order; validate input before sending (existing codec slices/masks silently). Keep explicit experimental gating. Existing sendTable sleeps command delay between all packets and retries writes; captured fast stream data intervals ~4–6ms, command ACK ~8–9ms, transaction ~57ms. Do not globally lower delays; add narrow variant-specific strategy only if needed. No blind retry of a partially accepted data report. Bounded latest-frame producer, no unbounded UI events queued in mutex; no persistent writes per frame. Validate volatility, arming and exit on 0109. Lighting Studio is separate native RGB implementation; do not compete with its active session.

### Global lighting
Existing encodeLightingData offsets match V4 captures: mode0, RGB1..3, colorful8, brightness9, speed10, direction11, AA55 at14..15. XML ranges up to 6 not 5. Mode IDs0..19, 80 custom. Off/zero slider semantics, direction codes and exact effect names are unverified on V4; AK820 catalog is reference, not verified. Capture sequence START SET/GET, LIGHT_MODE (04 13 arg8=1) SET/GET, raw data SET only, SAVE (04 02) SET/GET, FINISH (04 F0) SET only. Existing setRgbConfig sequence is close; compare byte-exact. Mirror only after complete success.

### Persistent per-key
Numeric slots0..127, [slot,R,G,B] at byte4*slot; holes zero, eight reports; ninth zero report with AA55 at offsets62..63. Current encodePerKeyTable uses TABLE_SLOTS and common encoder; verify output against fixture and validate only mapped LED IDs for V4. Existing customModePacket returns only 80 followed by zeros, but V4 captured mode packet contains brightness6 at offset9 and AA55 at14..15. Do not change all models to V4 behavior. V4 captured mode selection as global transaction then START, 04 23 arg8=9, ACK, nine data SETs, 04 02 SET/GET, F0 SET only. Existing setPerKeyRgb final FINISH defaults to handshake; compare and adjust V4 variant if necessary. No persistent table streaming.

### F5 readback — first candidate hardware operation
Capture 04 F5 arg8=9 SET, ACK GET, nine consecutive GETs. READ contains IDs even for unused slots; filter known map. Ninth read is slots128..143, not write-tail. Current getPerKeyRgb adds Cmd.SAVE after read based on AK820 reverse engineering. **Do not call this a pure read-only test on V4 until the extra command is justified.** Use V4 captured read sequence initially, without speculative SAVE/F0, after comparing full original capture. Test read completeness and slot consistency, color/brightness behavior, and unchanged persistent state. Blue example readback 0x5F at brightness2, not a validated scaling equation. No full hardware backup. Record observed response under 0109 before enabling write/read verification.

## 6. TFT and clock

The generic manifest reports 128x128 and up to255 frames; current generic screen-choice caps in variants.ts differ. Neither is the V4 geometry. V4 vendor XML: 240x135, RGB565le, 64800 bytes/frame, max135, single slot, 256 header, 4096 chunks. Existing standard tft codec matches inferred format: first byte count, one delay byte per frame (2ms units, verify), remaining header FF, pixel rows RGB565le, FF padding (verify capture). 1 frame => 65056 bytes before padding, 16 chunks; 135 frames => 8748256 bytes, 2136 chunks. Check computed values in tests, reject >135 before device I/O rather than silently truncating unless UI explicitly communicates truncation. Do not modify generic common cap.

04 72 with chunk count LE at offsets8..9, sub/slot field needs capture verification. FF68 bulk OUT 4096, ACK input 01 5A 02 observed. Existing sendDataChunk returns response or null and caller currently does not validate content; V4 must validate positive ACK and abort safely on timeout/failure, no speculative commit/retry. Existing uploader START, IMAGE, chunks, SAVE is reference, not verified V4 sequence. Compare full TFT capture for header, slot numbering, finalization, padding and timing before enabling. Do not use proStillChunks/PRO framing for V4 without evidence. Do not assert cancelled upload preserves previous animation until tested; partial writes may matter. Screen uploads high-risk; start one small still after RGB validated and owner approves. Test asymmetric image, primary colors, orientation; then two-frame GIF with known delays. Full 135-frame limit offline first; no unnecessary stress upload.

Clock: existing syncClock sends START, TIME 04 28 arg8=1, encodeTimeData(date,1) with handshake, SAVE. Owner observed 00 01 5A clock data. Compare full V4 packet offsets/date fields and ACK timings before writing; confirm local timezone handling and physical clock display. No assumption that clock sync is always safe on unidentified model.
